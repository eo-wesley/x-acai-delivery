# Retomada X-Açaí — 24/10/2026

## Problemas confirmados

- A resposta pública de `/api/default/store` não contém endereço, cidade,
  coordenadas, WhatsApp ou Pixel; o telefone é o placeholder `11999999999`.
- O seed existente usava aspas duplas no valor do Pixel dentro de SQL. PostgreSQL
  interpreta esse valor como nome de coluna e rejeita a atualização.
- PostgreSQL executa migrações no início do servidor, mas o seed mínimo depende de
  `DB_SEED_MINIMAL`. Alterar somente o seed não atualiza uma instalação existente.
  O valor dessa variável e a revisão implantada não foram verificados no servidor;
  portanto isso não determina sozinho a causa da divergência em produção.
- O workflow Readiness falhou ao usar `npm install` com uma versão de TypeScript
  diferente do lockfile. O workflow principal passou no build e falhou no login
  Docker Hub por ausência de credenciais (execuções 40074888978 e 40074907495).

## Correção

A migração `006_backfill_approved_default_store_config` preenche os dados aprovados
apenas do registro `id=default_tenant`, `slug=default`. Executa na transação de
migração, independentemente de `DB_SEED_MINIMAL`, e usa parâmetros SQL.

- Preenche campos nulos/vazios; substitui o telefone placeholder conhecido.
- Mantém telefone, WhatsApp e Pixel personalizados.
- Só completa a localização quando endereço/cidade são ausentes ou correspondem
  à loja aprovada e as coordenadas estão ambas ausentes ou já são as aprovadas.
- Preserva localização personalizada e pares incompletos para revisão explícita.
- Preserva estado aberto/fechado, preços, taxas de entrega, pedidos e outros tenants.
- Não cria loja ou item de demonstração durante a migração.

O seed utiliza a mesma configuração e sua reexecução é coberta pelos testes.
Os workflows usam instalação reproduzível; o build Docker de main funciona sem
publicação quando faltam credenciais. A branch production falha explicitamente
nessa situação, antes do deploy.

## Validação

```sh
npm run build --prefix apps/backend
npm test --prefix apps/backend
```

A suíte `test:store-config` cobre inserção, atualização, reexecução, campos vazios,
telefone placeholder, preservação de configuração personalizada, coordenadas
parciais, isolamento entre tenants e ausência de loja. SQLite usa memória;
`TEST_POSTGRES_URL` ativa a mesma suíte em PostgreSQL com tabelas temporárias e
valida o registro/reexecução da migração. O CI fornece PostgreSQL 16 isolado.
Nenhum teste lê o `DATABASE_URL` de produção.

## Aplicação operacional

Após implantação autorizada do backend, a inicialização normal aplica a migração
006. Conferir `/api/health` e `/api/default/store` e validar uma cotação autorizada.
Um push para main não confirma atualização do PostgreSQL produtivo. Não habilitar
o seed de demonstração para tentar corrigir uma loja existente.

As demais frentes mantêm seus portões: Vértice depende da aprovação do N01;
Copiloto depende de gabarito humano/piloto consentido; Prospecção depende da revisão
da demo; Goyaz de oferta/direitos/publicação; YouTube de canal/primeiro resultado.
Delivery-XAI permanece protótipo histórico incorporado ao aplicativo oficial,
com 59 testes locais aprovados na retomada anterior desta conversa.
